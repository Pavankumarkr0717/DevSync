# Research: System Design Canvas

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-31

Each decision gives the choice, why, and what was rejected. The Technical Context had no open
unknowns after these decisions.

## R1. Storage: one JSONB document per diagram, not relational nodes and edges

**Decision**: A `diagrams` table holds the diagram's metadata (id, workspace, name, revision,
counts, timestamps) and its whole content in one **`document jsonb`** column. A save replaces
the document as a unit, guarded by the revision (R6). Node and edge counts are copied into
plain columns so the list view never reads the document.

**Rationale**:
- The spec's unit of change is the whole diagram. A save sends nodes, edges and view together
  (FR-022), and conflicts are detected per diagram (FR-023). A document matches that exactly:
  one row, one compare-and-swap, no partial states.
- Canvas activity is bursty: a drag produces dozens of position changes. Normalizing would mean
  diffing the canvas into per-row inserts, updates and deletes on every save, or rewriting
  hundreds of rows. Either way, keeping node, edge and revision rows consistent needs
  multi-statement transactions. The user constraint says not to normalize canvas movements.
- Nothing in S04 queries *inside* diagrams (no "find all Databases across diagrams"), so
  relational columns would add cost without a reader.
- Schema evolution (R4) is a transform of one JSON document, not a database migration per
  change.
- PostgreSQL compresses large `jsonb` values and stores them out of line automatically (TOAST),
  and the list query (R7) never touches them.

**Trade-offs accepted**:

| JSONB document (chosen) | Relational `diagram_nodes` / `diagram_edges` (rejected) |
|---|---|
| One atomic write; revision CAS covers everything | Multi-row diff per save; consistency needs explicit transactions |
| Referential rules (edge → node) checked in code before storing | Foreign keys enforce edge → node in the database |
| Whole document rewritten per save (≤ 1 MiB, typically a few KB) | Small row updates, but many of them |
| Schema evolution in code (versioned transforms) | Evolution by EF migrations, with data migrations |
| No cross-diagram queries without JSON operators | Easy SQL over nodes and edges |

The missing database foreign keys are compensated by the authoritative validator (R5), which
runs on **every** write, plus tests for each rule (NFR-003).

**Alternatives considered**:
- *Relational nodes and edges*: rejected for the reasons above.
- *`text`/`bytea` instead of `jsonb`*: `jsonb` rejects malformed JSON at the database as a last
  line of defence and allows later inspection with SQL. The cost is that `jsonb` doesn't keep
  key order or whitespace, so the server stores its own canonical serialization (R5) and never
  relies on byte equality of stored JSON.
- *Separate `diagram_documents` table*: unnecessary. The list query projects columns, and TOAST
  keeps the document out of the main heap.

## R2. Canvas library: React Flow (`@xyflow/react` 12.12.0)

**Decision**: `@xyflow/react` 12.12.0 (released 2026-09-24; peer React ≥ 17, so React 19 works).
It provides:
- custom node and edge renderers;
- `Handle`s for connections and `isValidConnection`;
- `NodeResizer`;
- `Background` (grid), `Controls` and `MiniMap`;
- `snapToGrid`/`snapGrid`, `minZoom`/`maxZoom`, `fitView` and box selection
  (`selectionOnDrag`);
- keyboard-accessible, focusable nodes and edges, with Delete-key removal;
- `screenToFlowPosition` for drop placement.

The editor chunk is lazy-loaded, as Monaco is in 003.

**Rationale**: The user specified React Flow, and it covers every interaction in FR-013 and
FR-019 without custom canvas code. It renders to the DOM and SVG, so node text is real DOM text,
escaped by React, and accessible to tests.

**Alternatives considered**: hand-built SVG (a large amount of code for zoom, pan, selection and
resizing); `react-konva` and other canvas renderers (text not in the DOM, harder to make
accessible and to test); the older `reactflow` 11 package (superseded by `@xyflow/react`).

## R3. Document format v1

**Decision**: the `schemaVersion` is the first field. Metadata is an **array of `{key, value}`
pairs**, never an object.

```json
{
  "schemaVersion": 1,
  "nodes": [
    { "id": "…", "type": "microservice", "title": "Orders", "description": "",
      "metadata": [{ "key": "owner", "value": "payments" }],
      "position": { "x": 120, "y": 80 }, "size": { "width": 180, "height": 80 } }
  ],
  "edges": [ { "id": "…", "source": "…", "target": "…", "label": "REST" } ],
  "viewport": { "x": 0, "y": 0, "zoom": 1 }
}
```

- **Types** (stable, snake_case): `client`, `api_gateway`, `microservice`, `database`, `cache`,
  `message_queue`, `load_balancer`, `external_service`.
- **IDs**: generated by the client (`crypto.randomUUID()`), so offline edits and drafts never
  need the server to name things. The server accepts any 1–64 character string of
  `[A-Za-z0-9_-]` and only enforces uniqueness and references.
- **`viewport`** may be `null` (never saved): open with fit-to-view (FR-020).
- The full JSON Schema is
  [contracts/diagram-document.v1.schema.json](./contracts/diagram-document.v1.schema.json).

**Rationale**:
- **Metadata as an array**: keys are user text. As object keys they could collide with
  prototype names (`__proto__`, `constructor`) in JavaScript, and duplicate keys would vanish
  silently in JSON parsers. An array keeps order and lets the validator detect duplicates
  (case-insensitive).
- **Snake_case types**: stable wire values, independent of display names. The labels ("API
  Gateway") live in the client's type registry.
- **Version first**: tools and humans can read the version before parsing the rest.

## R4. Schema versioning and migration

**Decision**:
- **Current version**: `DiagramSchema.CurrentVersion = 1`. Every stored document records its
  version; the `diagrams.schema_version` column mirrors it, for queries and monitoring.
- **Reading**: the server deserializes the stored document according to its version and runs
  the **upgrade chain** `v(n) → v(n+1)`, a pure-function step per version in
  `DiagramDocumentUpgrader`, until it reaches the current version. The upgraded document is
  returned; the stored row is **not** rewritten on read, only on the next successful save
  (FR-028). Reading never writes, so a read can't race a save.
- **Writing**: clients must submit `schemaVersion == CurrentVersion`. Anything else gets 400
  `unsupported_schema_version`. Clients never write old formats.
- **A stored version newer than current**, which only happens if the app is rolled back after a
  newer release stored something: GET returns metadata, `document: null` and
  `unsupportedSchemaVersion: <n>`. PUT is refused with 409 `stored_version_unsupported`,
  unless the request explicitly asks to replace it (`?replaceUnsupported=true`; offered in the
  UI as "Start over", Owner or Editor). That meets FR-029: never overwritten silently.
- **Unreadable stored documents** (corruption) are treated like an unsupported version, with a
  logged error that has no content.
- **Adding a version later**: bump `CurrentVersion`, add one upgrade step, its unit tests, and a
  fixture of the old version. No database migration is needed unless a mirrored column changes.

**Rationale**: forward-only, pure upgrade steps are simple to test, and the first real step can
be added without touching storage. Because there is only v1 today, the upgrade machinery is
tested with a **test-only v0 → v1 step** registered through the upgrader's constructor. The
production chain is empty, so no shipped code imagines a future format.

**Alternatives considered**:
- *Upgrade on read and write back immediately*: a GET would mutate data, and it could race
  saves. Rejected.
- *EF migration that rewrites all documents*: possible later for bulk upgrades, but
  unnecessary while reads upgrade lazily.

## R5. Server validation (authoritative) and canonical storage

**Decision**: the save pipeline is:
1. Read the raw body with the shared bounded reader from 003, capped at **1 MiB** (413
   `content_too_large`). The content type must be `application/json` (415).
2. Parse with strict `System.Text.Json` options:
   - `AllowDuplicateProperties = false` (.NET 10), so a key repeated inside an object is
     malformed;
   - `UnmappedMemberHandling = Disallow`, so **unknown properties are rejected**;
   - no comments or trailing commas;
   - numbers must be finite.

   Failure → 400 `invalid_diagram` with problem `malformed`.
3. Check the version first: not 1 → 400 `unsupported_schema_version`.
4. Run the pure domain validator, `DiagramValidator`, over the typed document. It collects **all**
   problems, up to 50, each with a stable code, a JSON path and a message (FR-033, FR-036):

| Code | Rule |
|------|------|
| `too_many_nodes` / `too_many_edges` | ≤ 500 nodes, ≤ 1,000 edges |
| `invalid_id` | id is 1–64 characters of `[A-Za-z0-9_-]` |
| `duplicate_node_id` / `duplicate_edge_id` | ids unique within nodes and within edges (one id may not be both a node and an edge either) |
| `unknown_node_type` | type is one of the 8 values |
| `unknown_node_reference` | an edge's `source` or `target` is not a node id of this document |
| `self_connection` | `source != target` |
| `duplicate_edge` | at most one edge per (source, target) pair |
| `text_too_long` / `text_required` | title 1–100, description ≤ 2,000, label ≤ 200, metadata key 1–50, value ≤ 500 (Unicode code points) |
| `invalid_text` | control characters, except `\n` and `\t` in descriptions; lone surrogates |
| `too_many_metadata` / `duplicate_metadata_key` | ≤ 20 entries; keys unique ignoring case |
| `out_of_range` | position within ±100,000; size 40–2,000; viewport zoom 0.1–4; viewport x/y within ±10,000,000; all finite |

5. Any problem → 400 `invalid_diagram` with `problems: [{ code, path, message }]`. **Nothing is
   stored.**
6. Serialize the typed, validated document back to **canonical JSON** (fixed property order, no
   unknown fields; text exactly as sent). That is what goes into `jsonb`. Unknown or extra data
   can never reach storage, which also covers the "no executable code" constraint: metadata
   values are inert strings that are length-limited and control-character-free, never
   evaluated, and rendered by React as text.

**Client-side checks** (FR-034) mirror the cheap rules for instant feedback: no self or
duplicate connections can be drawn (`isValidConnection`), deleting a node deletes its edges, and
inputs enforce lengths and ranges. The client never relies on them; the server re-runs
everything.

**Alternatives considered**:
- *JSON Schema validation library on the server*: adds a dependency and still can't express
  "edge references an existing node" or "unique ignoring case". The JSON Schema file is kept as
  **documentation and a contract test fixture**, and the C# validator is authoritative.
- *Lenient parsing* (ignore unknown fields): rejected, because extra payload would be stored
  silently.

## R6. Concurrency: revision compare-and-swap, as in 003

**Decision**: `diagrams.revision` starts at 1 (empty document) and grows by one on every content
save. The document is saved with `PUT …/diagrams/{id}/document` and `If-Match: "<revision>"`, as
one statement:

```text
UPDATE diagrams SET document, schema_version, node_count, edge_count, revision = revision + 1, …
WHERE id = @id AND workspace_id = @w AND revision = @expected
```

- 0 rows → a follow-up read tells **412 `revision_conflict`** (with `currentRevision`) from
  **404** (deleted).
- 428 when `If-Match` is missing.
- Renaming doesn't change the revision.

**Rationale**: the proven 003 mechanism, reusing its `If-Match`/`ETag` helpers and the client's
conflict UI. No merge in S04 (no real-time collaboration).

## R7. Diagram lifecycle and workspace relationship

**Decision**:
- **Rows**: `diagrams.workspace_id` references `workspaces` with ON DELETE CASCADE. Name rules
  are 1–100 characters after trim, with no control characters.
- **Name uniqueness**: a unique index on (`workspace_id`, `normalized_name`), where the
  normalized name is the upper-invariant form.
- **Create** locks the workspace row (`SELECT … FOR UPDATE`, as 003 does for its tree), then
  checks the 50-diagram limit and the name, then inserts. That prevents racing past the limit.
- **Rename** relies on the unique index (409 `diagram_name_taken`).
- **Delete** is a single statement.
- **List** projects `id, name, revision, node_count, edge_count, updated_at` without the
  document.

**Rationale**: matches the clarified role model (create and rename: Owner and Editor; delete:
Owner) and the files feature's locking pattern.

## R8. Authorization: two new operations in the S02 permission table

**Decision**: add `WorkspaceOperation.EditDiagrams` (Owner, Editor: create, rename, save
content) and `DeleteDiagrams` (Owner). Reading uses `Read`. Every route uses
`RequireWorkspace(op)`, which reads the role per request: non-member → 404, member without
permission → 403.

**Alternatives considered**: reusing `EditFiles`/`DeleteFiles`. The role sets are identical
today, but separate operations keep the table readable and let the two diverge later without
a breaking change.

## R9. Frontend state: persisted document vs transient interaction

**Decision**:

| State | Where | Notes |
|-------|-------|-------|
| Diagram list, loaded document, revision | RTK Query `diagramsApi` | Server state; tags `DiagramList:ws`, `Diagram:id` |
| **Persisted diagram data being edited** | Redux `diagramEditorSlice`, **normalized** with `createEntityAdapter`: `nodes` and `edges` as `{ ids, entities }`, plus `viewport`, `baseRevision`, `status`, `unsupported` | One open diagram at a time. Only committed changes are dispatched |
| **Transient interaction**: in-flight drag and resize positions, selection, hover, connection being drawn, live viewport during pan and zoom | React Flow's internal store, plus the canvas component's local state | Never in Redux, never saved, never in a draft |
| Grid snapping on/off | `localStorage` per person (FR-019) | UI preference |
| Autosave timing | `AutosaveController` from 003 (unchanged) on the **canonical serialized document** | Its "text" is the canonical JSON string |
| Drafts | `drafts.ts` from 003, keyed `diagram-<id>` | Same restore and conflict semantics |

**Commit points** are when React Flow changes become Redux actions:
- drag stop, so a drag is **one** commit (SC-009);
- resize end;
- connect;
- delete, of nodes and their edges, or of an edge;
- add from the palette;
- configuration panel edits (each change; the 1 s autosave debounce absorbs typing);
- node type change.

**Viewport is not a commit point.** Pan and zoom never trigger a save on their own. Each save
includes the viewport *as it is at that moment* (read from React Flow when serializing). This
avoids the trap where merely panning bumps the revision and causes conflicts for co-editors.
The spec's "whoever saves last sets the view" still holds.

**Rendering**: React Flow runs **controlled** for structure (nodes and edges are derived from
Redux by memoized selectors that map entities to React Flow nodes), but **positions during a
drag** come from React Flow's own `applyNodeChanges` in local state. The local state is
re-seeded from Redux when Redux changes (load, commit, restore, reload-latest). In short:
Redux is the source of truth for what is saved; React Flow is the source of truth for what is
moving right now.

**Rationale**: Dispatching on every drag frame would push up to 60 Redux updates per second
through Immer over 500 nodes and wake every subscriber. Keeping transient state local is the
standard React Flow pattern and is what the user constraint asks for.

**Canonical serialization**: nodes and edges in id order, with fixed property order. Two equal
diagrams serialize identically, so "no change since last save" is a string comparison, as for
files.

## R10. Node components: one renderer and a type registry

**Decision**: a single custom React Flow node type `component` renders every component. A
**type registry** (`componentTypes.ts`) maps each of the 8 types to its display name, inline
SVG icon, accent colour, default title and default size. The registry also drives the palette.
- **Node**: icon, title, a truncated description line, 4 handles (top and left targets, bottom
  and right sources; any handle can start a connection), and a `NodeResizer` when selected and
  editable.
- **Edge**: one custom edge (`labelled`) with an arrow marker and its label rendered through
  `EdgeLabelRenderer` as text.

**Rationale**: eight near-identical components would duplicate code; the registry is one place
to add a ninth type later. Inline SVG icons avoid an icon-font dependency (constitution XI).

## R11. Interaction details

| Interaction | Behaviour |
|-------------|-----------|
| Zoom | 10%–400% (`minZoom 0.1`, `maxZoom 4`); Controls, wheel and pinch, +/- keys; zoom % shown in the toolbar |
| Pan | Drag on empty canvas, or space plus drag. Arrow keys pan when no node is focused |
| Fit to view | Toolbar button and on open when no viewport is saved; padding 0.15; an empty diagram resets to `{0,0,1}` |
| Selection | Click; Shift/Ctrl-click to add; drag on empty canvas with Shift for a box; selected nodes move together |
| Grid | `Background` lines with gap 20; `snapToGrid` with `[20,20]`; toggle stored per person |
| Add | Drag from the palette onto the canvas (dropped at the pointer, snapped), or click a palette item (placed at the view centre, offset if occupied) |
| Delete | Delete or Backspace on the selection, or the panel's delete button. A node takes its edges with it |
| Read-only (Viewer, or unsupported version) | `nodesDraggable`, `nodesConnectable`, `elementsSelectable` stays true for inspection, no resizer, no palette, panel inputs disabled, Delete key disabled |

## R12. Limits per hop

The document body is capped at **1 MiB**: the API reads at most 1 MiB + 1 bytes and returns 413
above that. nginx already allows 2 MiB from 003.

A diagram at every count limit with long texts could in theory exceed 1 MiB (500 nodes ×
13 KB), so the byte cap is a separate, explicit limit with its own message. Typical diagrams
are a few KB.

## R13. Logging

Diagram endpoints log only workspace and diagram ids, revisions, counts and problem codes.
They never log names, titles, labels, descriptions, metadata or documents (NFR-001). An
integration test scans the logs for marker strings.

## R14. Migration

One EF migration, `SystemDesignCanvas`, adds the `diagrams` table. It is purely additive;
existing workspaces start with no diagrams.
